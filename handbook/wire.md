# The wire

How bytes move between a driver and a hoardDB server. Language-neutral; binds every driver. The
vectors (`testdata/driver-vectors/v1.json`) win where they disagree with this page.

## 1. Transport

- **TCP + TLS, TLS 1.3 minimum.** There is no plaintext mode and none may be offered.
- **ALPN is mandatory: offer exactly `hoarddb/1`.** The server re-checks the negotiated protocol after
  the handshake and refuses any other value, including none (a client that offers no ALPN at all). The
  refusal is an `OpError` `UNSUPPORTED_VERSION` with an all-zero request ID, then close (section 8).
- **Default driver port: 7433.** A URI with no port means 7433.
- **The server binary listens on loopback (`127.0.0.1:7433`) by default.** The container image listens
  on every interface; what is reachable is decided by which ports are published. A driver never needs
  to know this, but a developer whose connection is refused from another machine does: say so in the
  "unreachable" message.
- The internode port (by default the ring port plus one, `4434`) is for nodes, not drivers. A
  node-to-node opcode sent on the driver port is refused.
- The server's certificate is self-signed ed25519; there is no certificate authority and no hostname in
  it. Trust is by key fingerprint: `trust.md`.

## 2. Frames

Every message, in both directions, is one frame:

```
+---------+------------------+---------+--------------------+------------------+
| Ver (1) | Length (4, LE)   | Op (1)  | Request ID (16)    | Payload (N)      |
+---------+------------------+---------+--------------------+------------------+
```

- The header is **22 bytes**. `Length` is little-endian and counts **opcode + request ID + payload**
  (`1 + 16 + N`); it does not count the version byte or itself.
- `Length` must be at least **17** and at most **32 MiB** (33,554,432). `Ver` must be **1**.
- A codec reads the 5-byte prefix, checks `Ver` and `Length` **before** allocating the body, then reads
  exactly `Length` bytes. A driver must never allocate from an unchecked length word.
- **Request ID**: 16 random bytes (a UUIDv4 is fine) generated by the client per request, unique among
  the requests in flight on that connection. The server echoes it verbatim on the response. Correlate by
  it always, even with one request in flight: a response whose ID matches no request in flight is a
  protocol violation, and the connection is torn down, not guessed at. **One exception:** a
  connection-level refusal (section 8) carries an **all-zero** request ID and is followed by a close;
  read it as the answer to whatever was in flight.
- **What the server does with a bad frame.**
  - A length word over 32 MiB is **answered**: the server reads the opcode and request ID and writes an
    `OpError` `INVALID_ARGUMENT` **echoing that request ID**, with a message naming the opcode, the size,
    the 32 MiB limit and the remedy (split the request into smaller ones). On an
    authenticated connection whose length word is at most 64 MiB the server then discards the body and
    keeps the connection; past that, or before AUTH, it answers and closes.
  - A version byte other than 1, or a length under 17, is **not answered**: the server closes the
    connection and the driver sees EOF or a reset.
  - So a driver **refuses an oversize frame itself, before writing a byte of it**, with a local
    `INVALID_ARGUMENT` error that gives the arithmetic (`1 + 16 + payload` against 33,554,432). The
    server's answer exists for clients that do not.
- **Payloads are BSON documents**, except that `RING_KEYED`, `RING_BATCH` and `RING_GET_MANY` start with a binary prologue (section 11.2). An empty payload is legal
  (`PING` carries none; `PONG` answers with an empty payload: the transport answers it before any handler runs).

## 3. BSON payload rules

- **Field names are exact and come from the vectors and `operations.md`, never from a guess.** Many
  carry an underscore: `write_outcome`, `copies_confirmed`, `served_by`, `state_seq`, `bucket_id`,
  `decl_version`, `schema_version_seen`, `database_id`, `guard_field`, `document_truncated`,
  `protocol_version`, `server_version`, `token_expires_at`, `token_deadline`, `password_min_length`. Each
  is what it is; a driver pins every name in its own request and response types.
- **Decode any numeric width** for the integer fields of the admin and auth documents. The server sends
  `int32` or `int64` depending on the field and may change width within the range a field holds. For the
  ring request and reply documents of section 11.1 the vectors fix the widths (`limit` is `int32`,
  `epoch` and `state_seq` `int64`), and a codec refuses a widened integer.
- **Ignore fields you do not know.** The server adds optional fields to answers without a protocol
  version change. A decoder that fails on an unknown field breaks on the next server release.
- **Absent means absent.** An optional field that is empty is not sent at all; it does not arrive as a
  zero. A heap's `priorities` and a queue's `position` are sent for their stores even at 0, so a missing
  one never means 0.
- **Documents pass through.** A stored document comes back as a nested BSON document (`document`,
  `elements[]`), byte for byte as stored. A driver gives it to the caller
  without re-encoding it.
- **Field order in a request does not matter to the server.** A driver may send fields in any order and
  may omit an optional field whose value is empty.
- **A document's field order is not kept.** The server holds a document as a map: the fields of a
  stored document (at every level) come back in an order the server chooses, which can differ from the
  caller's and between two documents written alike. A driver compares documents field by field, never
  by their bytes, and does not promise its caller an order.
- **A vector's `allowed_fields`** lists exactly what a driver may send for each request. A field a
  node sends to another node is never a client's.

## 4. The opcode table

A response does not always carry the request's own opcode, and any error answer is `ERROR` (`0xA2`) in
place of the success opcode. The opcodes a driver sends:

| Request | Hex | Success response opcode | Payload |
|---|---|---|---|
| `AUTH` | 01 | `AUTH_OK` 02, or `AUTH_FAIL` 03 | auth response / auth refusal (`auth.md`) |
| `PING` | A0 | `PONG` A1 | (empty) |
| `RING_LIST` | DA | `RING_REPLY` DF | section 11.1 |
| `RING_COUNT` | DB | `RING_REPLY` DF | section 11.1 |
| `RING_KEYED` | DC | `RING_REPLY` DF | section 11.3 and 11.4 |
| `RING_ADMIN` | DD | `RING_REPLY` DF | section 11.1 |
| `RING_TOPOLOGY` | DE | `RING_REPLY` DF | section 11.6 |
| `RING_BATCH` | E0 | `RING_REPLY` DF | section 11.8 |
| `RING_GET_MANY` | E1 | `RING_REPLY` DF | section 11.1 |

The ring opcodes carry every verb a driver needs: databases and buckets (`RING_ADMIN`), documents and
stores (`RING_KEYED`, `RING_BATCH`, `RING_GET_MANY`), listing and counting (`RING_LIST`, `RING_COUNT`) and
routing (`RING_TOPOLOGY`). Section 11 has the bytes and `operations.md` the meaning of each verb. The
earlier single-store opcodes (`PUT`, `FIFO_PUSH`, `BLOB_WRITE`, `BATCH_PUT`, `SCAN`, `CREATE_BUCKET` and
the rest of `0x10` to `0x8F`, `0xC1` and `0xD0` to `0xD9`) belong to the engine the ring replaces. A
driver does not send them, and this handbook does not document them. A ring node still answers them from
that earlier engine, which keeps its own databases and buckets: nothing created through them is visible to
the ring opcodes, and nothing created through the ring is visible to them. They are not part of the API.
The root package `hoarddb` of the Go module, the Node.js driver and the Python driver send them; the
package `ring` of the Go module sends the ring opcodes (`api-go.md`).

**Outside the application API** (the vectors do not cover them): `CLUSTER_ADD` 97, `MIGRATE` 98
and `CLUSTER_REMOVE` 99 are operator triggers; `DUMP_START`/`DUMP_CHUNK`/`DUMP_DONE` A5 to A7 and
`RESTORE_START`/`RESTORE_CHUNK`/`RESTORE_DONE` A8 to AA are the backup, root only today. User
administration with a client-derived Argon2id credential (never a plaintext password) is `RING_ADMIN`'s
user commands, `auth.md` sections 6 and 7. The codec module `hoarddb-wire` v0.1.0 and the vectors in this
repository do not carry those commands yet.

**Never sent by a driver.** Node-to-node opcodes are refused on the driver port by name, with
`INVALID_ARGUMENT` echoing the request ID, and the connection is then closed: `GOSSIP` 90, `REPL_PUSH`
91, `REPL_ACK` 92, `MIGRATE_START`/`DATA`/`DONE` 93 to 95, `CLUSTER_PROPOSE` 96, `CLUSTER_PROBE`/`CLUSTER_PROBE_REPLY` 9A and 9B, `VERSIONED_GET` 9D,
`MEMBERSHIP_CHANGE` 9E, `STREAM_OPEN`/`DATA`/`END`/`ACK` B0 to B3, `AUTH_CONFIG_PUSH`/`ACK` C4 to C5.
**Reserved**: `0x04`. Any other byte is answered `INTERNAL` ("no authorization rule is declared for opcode
... (default deny)").

## 6. Capabilities

`AUTH_OK` carries `capabilities[]`. A driver records the list at AUTH and **ignores strings it does not
know**. The server advertises `pipelining`, `get_fast`, `write_concern`, `consistent_get`, `auth_token`,
`bucket_rf`, `query_pipelining` and `batch`; only `auth_token`, which gates tokens (`auth.md`), concerns a
ring driver, and the rest name features of the earlier engine. The ring opcodes need no capability, and there is none for
the write outcome: read the fields when they are present (`errors.md`).

## 7. Concurrency on one connection

- The server reads ahead up to **4 frames or 1 MiB** per connection (operator-tunable) and runs each
  admitted frame **concurrently**. With more than one request in flight, **neither response order nor
  execution order is guaranteed**. A client that writes too far ahead is not refused; the server stops
  reading and TCP backpressure slows it.
- A driver may keep **one request in flight** per connection (lockstep, with several connections in a
  pool), which needs no ordering contract, or **pipeline**: send several requests and match each reply
  to its request by request ID, accepting that replies arrive in any order. Either way the connection is
  a request-ID demultiplexer (a writer lock, one reader, a table of waiters by request ID).
- Closing the connection is the only cancel. A handler error the server cannot answer (`INTERNAL`) still
  closes the connection, and the requests in flight on it get no answer.
- `RING_LIST` and `RING_COUNT` read every document of a bucket, so they can be slow. Keep
  latency-sensitive keyed reads and long listings on **separate connections**.

## 8. Refusals at the connection level

These complete the TLS handshake, send exactly one `ERROR` frame with an **all-zero request ID**, and
close:

- `OVERLOADED` (`0x0D`): the server's global connection budget, or its per-address cap, is full. **Not
  fatal to a pool**: back off that one dial; the connections already open are fine.
- `UNSUPPORTED_VERSION` (`0x0A`): ALPN not served (section 1).

Any non-`AUTH` request before AUTH succeeds is answered `NOT_AUTHENTICATED` (`0x0C`), "connection not
authenticated; send AUTH first", and the connection stays open. `PING` is answered before AUTH, so a
pre-authentication liveness probe is legal.

The server closes every live connection of a user who is dropped or disabled. A pooled connection can
therefore disappear for an authorization reason, not a network one; the next AUTH on a new connection
says why.

## 9. Timeouts, heartbeats, budgets

Server defaults (operator-tunable; a driver does not read them from the server):

| What | Default |
|---|---|
| Idle timeout: a connection with no frame for this long is closed by the server, re-armed between frames, jittered ±10 % per connection. **It runs even while a request is in flight**, so a single request that takes longer than this on an otherwise silent connection can lose its connection | 300 s |
| Frame timeout: one frame's header and body, and each response write | 30 s |
| Connections per source address | 64 |
| Connections in total | 1,000 |

- **The server never sends a driver a `PING`.** A driver sends `PING` on idle pooled connections well
  inside the idle timeout (every 60 s is the recommendation) and treats `PONG` as the only proof of
  life; or closes connections it has not used for 120 s. TCP keepalive is a backstop only.
- **Keep pools small.** The per-address cap is shared by every process on a machine.
- **A per-request timeout** applies when the caller gives none (the Go client: 30 s). Without a read
  deadline a driver hangs forever on a dropped connection.
- Do not run a single request that can take longer than the idle timeout on an otherwise silent connection.

## 10. Size limits

A driver enforces **only the frame limit** itself and passes the server's refusal through for the rest:

| Limit | Value | When exceeded |
|---|---|---|
| Frame | 32 MiB (33,554,432 bytes), fixed | refused by the driver before sending (section 2) |
| A request before AUTH succeeds | 64 KiB, fixed | `INVALID_ARGUMENT`, then the server closes the connection |
| A document | no limit of its own: it and everything else in its request stay under the frame limit | `INVALID_ARGUMENT` |
| One `RING_BATCH` or `RING_GET_MANY` | 255 operations, fixed | refused by the driver before sending; the server refuses the frame with `INVALID_ARGUMENT`, nothing written |
| The answers of one batch | 16 MiB kept whole | answers past the budget are not kept whole; error answers are always kept (section 11.8) |
| One page of `RING_LIST` | 100 documents by default, at most 10,000 and at most 16 MiB | the page ends early and its cursor continues from there |
| One page of a store list | 1 to 1000 elements | `INVALID_ARGUMENT` |
| A peek | 1 to 100 elements | `INVALID_ARGUMENT` |
| Any response frame | 32 MiB, fixed | replaced by `RESULT_TOO_LARGE` echoing the request ID: ask for a smaller page, project fewer fields, or narrow the filter |
| Database or bucket name | 255 bytes of UTF-8, fixed | the create is refused before anything is written |
| A field name | 1 to 255 bytes, fixed | the create or alter is refused |
| A user name | 1 to 1021 bytes of UTF-8, no control character, fixed | the command is refused |

## 11. Ring opcodes (0xDA to 0xE1)

The ring client wire: seven opcodes a driver sends to a ring node, and `RING_REPLY`, their success reply.
The bracketed references (client-wire, conventions, queries, each with a section) name the server's design
documents the statement comes from. Those documents are not part of this repository: what a driver can
check is the vector group `ring` in `testdata/driver-vectors/v1.json` and the codec module
`github.com/hoarddb/hoarddb-wire`. The vectors win for bytes.

The frame (section 2: 22-byte header, 32 MiB cap), TLS and `AUTH` are unchanged, and `AUTH` comes before any
ring opcode (client-wire section 4). A refusal is never a `RING_REPLY`: it is `ERROR` (`0xA2`) with the
payload of section 11.5, so the opcode tells success from refusal (client-wire section 1).

### 11.1 The ring opcode table

| Request | Hex | Success response opcode | Payload |
|---|---|---|---|
| `RING_LIST` | DA | `RING_REPLY` DF | request: BSON `{database, bucket, filter?, fields?, limit?, cursor?, epoch?}`, in that member order, **no prologue** (the epoch is a BSON field); reply: `{entries, more?, cursor?, epoch, state_seq}`, `entries` a concatenation of `[slot:2 BE][uvarint idlen][encID][uvarint bodylen][body]` records. Read-only (client-wire section 1; queries Formats) |
| `RING_COUNT` | DB | `RING_REPLY` DF | request: BSON `{database, bucket, filter?}` and nothing else (a count takes no limit); reply: `{count, epoch, state_seq}`, `count` int64. Read-only (queries Formats) |
| `RING_KEYED` | DC | `RING_REPLY` DF | request: prologue (20) + class byte (1) + header (40) + class form (section 11.3); reply: the keyed reply of section 11.4 (client-wire sections 1 and 2) |
| `RING_ADMIN` | DD | `RING_REPLY` DF | request: one BSON command document `{cmd, ...}`; reply: a body of its own per command. Not a read. Commands in client-wire section 1: `create_database`, `create_bucket`, `describe_bucket`, `show_buckets`, `show_databases`, `describe_database`, `describe_node`, `alter_bucket`, `drop_bucket`, `seeding_status`, `seeding_retry`, `seeding_forget`, the membership commands `join`, `promote` and `replace_node`, and the user commands `create_user`, `alter_user`, `drop_user`, `grant_role`, `revoke_role`, `show_users` and `describe_user` (the server answers them; `hoarddb-wire` v0.1.0 has no encoder for them and no vector row here sends one). There is no `drop_database` or `alter_database`: they are not available yet (`leave` and `remove_node` are refused). The per-command layout is pinned by the vector rows `ring admin: ...` (section 11.9) |
| `RING_TOPOLOGY` | DE | `RING_REPLY` DF | request: BSON `{epoch, state_seq}`, both int64, no prologue; reply: `{epoch, state_seq, unchanged: true}`, or `{epoch, state_seq, members, witnesses?, voters?, table, databases[{name, id, rf}]}` (section 11.6). Read-only; any authenticated session may call it (client-wire section 4) |
| `RING_REPLY` | DF | (the success reply of the other six) | BSON, matched to its request by the 16-byte request ID (client-wire section 1) |
| `RING_BATCH` | E0 | `RING_REPLY` DF | request: prologue (20) once + count byte (1 to 255) + that many `RING_KEYED` write bodies; reply: `{outcome, answers[], epoch, state_seq}` (section 11.8). Not a read (client-wire sections 1 and 7) |
| `RING_GET_MANY` | E1 | `RING_REPLY` DF | request: prologue (20) once + count byte (1 to 255) + that many keys, each a 2-byte big-endian length and a `RING_KEYED` `get` (`0x81`) or `get_fields` (`0x89`) body; reply: `{outcome, answers[], epoch, state_seq}` as `RING_BATCH`'s, one answer per key in request order, a miss `found: false`. Read-only; no atomicity, no snapshot; no fallback to lone gets (client-wire section 8) |

**The ring's BSON is canonical, and a driver's codec refuses what is not.** The vector rows `ring list refused`,
`ring count refused`, `ring topology refused` and `ring reply refused` (and their `reply` direction) refuse,
with `INVALID_ARGUMENT`: members out of the order above; a member the table does not define; a widened
integer (`limit` is int32, `epoch` and `state_seq` int64, `copies_confirmed` int32); a default that is written
instead of omitted (`epoch` 0, `deduped` false); a truncated document; a byte after the document. `fields` on a
`RING_LIST` is a non-empty array of strings, each name once, written between `filter` and `limit`.

### 11.2 The client prologue (20 bytes)

`RING_KEYED`, `RING_BATCH` and `RING_GET_MANY` start their payload with this prologue; `RING_LIST`, `RING_COUNT`,
`RING_TOPOLOGY` and `RING_ADMIN` carry none (conventions section 6; client-wire section 1):

```
+-----------------+--------------------+---------------------+
| epoch (8, BE)   | state_seq (8, BE)  | deadline_ms (4, BE) |
+-----------------+--------------------+---------------------+
```

- **Big-endian**, unlike the frame's little-endian length word.
- `epoch` is the epoch of the client's topology table; `0` with `state_seq` `0` means "route it for me".
  `state_seq` is informational. `deadline_ms` `0` means no deadline; otherwise it bounds the owner's
  write-concern wait to the lower of `deadline_ms` and `replication.wc_timeout_ms`
  (conventions section 6).
- A payload shorter than 20 bytes is refused `INVALID_ARGUMENT` (vector `ring keyed refused: shorter than the
  prologue`).

### 11.3 The keyed body and its class bytes

```
+---------------+------------+-------------+------------------+
| Prologue (20) | Class (1)  | Header (40) | Class form (N)   |
+---------------+------------+-------------+------------------+
```

The 40-byte header is `bucket id (8) | declaration version (8) | schema_version_seen (8) | prevEnd (16)`
(conventions Formats 1); the 16 `prevEnd` bytes are zero in every ring vector. A ring request names a bucket by
id and carries no database name (client-wire section 3); a driver learns the ids from `RING_ADMIN`
(`create_bucket`, `describe_bucket`, client-wire section 6). `encID` is the document id's encoding
(conventions sections 3 and 5). An unknown class byte, a truncated body and a byte after the form are each
`INVALID_ARGUMENT` (vectors `ring keyed refused: ...`).

| Class | Name | Kind | Form after the header |
|---|---|---|---|
| 01 | `INSERT` | write | `[encID][idLen:4][idValue][fieldCount:2][field x n]`, `field = [fieldID:2][valueLen:4][value]` (conventions section 9.1) |
| 02 | `UPDATE` | write | `[encID][opCount:2][op x n][trailer]`, `op = [opCode:1][fieldID:2][valueLen:4][value]`; the trailer is the guard and return byte below |
| 03 | `UPSERT` | write | the `INSERT` form |
| 04 | `DELETE` | write | `[encID][trailer]` |
| 05 | `STORE_VERB` | write | `[encID][fieldID:2][verb:1][argLen:4][arg]`; `verb` 1 push, 2 pop, 3 take, 4 put, 5 inc; `arg` a canonical BSON document (conventions section 9.1) |
| 06 | `CLAIM` | write | `[encID][fieldID:2][count:2][now:8][nonce:16]` |
| 07 | `ACK` | write | `[encID][fieldID:2][leaseID:16][now:8]` |
| 08 | `RELEASE` | write | `[encID][fieldID:2][leaseID:16][now:8]` |
| 09 | `EXTEND` | write | `[encID][fieldID:2][leaseID:16][now:8][until:8]` |
| 81 | `get` | read | `[encID]` and nothing after it (vector `ring keyed refused: trailing byte`) |
| 82 | `peek` | read | not stated in client-wire; the bytes are in the vector rows `ring keyed: ...`. A peek count is 1 to 100 (client-wire section 2) |
| 83 | `store list` | read | as `peek`; a page is 1 to 1000, a cursor pages further (client-wire section 2) |
| 84 | `store count` | read | as `peek` |
| 87 | `lease_get` | read | `[encID][fieldID:2][leaseID:16]`, nothing after; a `fifoStore` or `lifoStore` field only; an all-zero lease ID is refused (client-wire section 2) |
| 88 | `store_get` | read | `[encID][fieldID:2][keyLen:2][key]`, key 1 to 1024 bytes; a `fifoStore`, `lifoStore` or `blobStore` field is `INVALID_ARGUMENT` (client-wire section 2) |
| 89 | `get_fields` | read | `[encID][count:1]` then per name `[len:1][name]`; 1 to 64 declared scalar names, 1 to 255 bytes each, none twice; no field ID, limit or cursor (client-wire section 2) |

**The trailer of `UPDATE` and `DELETE`.** Both forms end in one byte, always present: bit 0 says a guard section
follows, bits 1 and 2 are the return mode (0 none, 1 after, 2 before; `after` on a `DELETE` is `INVALID_ARGUMENT`), and
every other bit is refused, so a body from a newer build is never read as today's. The guard section is
`[n:1][(fieldID:2][valueLen:4][typed value]) x n]` with `n` 1 to 16, field IDs from 2 up in ascending order with no
repeats, each value the type byte then the BSON bytes. A term holds when the stored value equals it under the match
the scan uses (an int, a long and a double of one number are equal); a `null` term also holds when the field was
never set. A guard names declared scalar fields only: a store field or an undeclared ID is `FIELD_TYPE`. The guard
rides the client body and is never logged. Vectors `ring update guard applied` and `ring update guard refused` pin
both.

`0x85` and `0x86` are not on the wire (client-wire section 2). Reads take no position and write no log record.
The write forms' `now` is stamped by the owner (conventions section 9.1). The `UPDATE` operator codes and the
`STORE_VERB` `arg` shapes are in conventions section 9.1, and the field names of a store verb's `arg` are one
letter each.

### 11.4 The keyed reply

A `RING_REPLY` to a `RING_KEYED` is one BSON document; an absent field is omitted (client-wire section 2):

| Field | Type | Meaning |
|---|---|---|
| `write_outcome` | string | `applied`, `applied_degraded`, `not_applied` or `unknown`; absent on a read. `not_applied` is an `UPDATE` or `DELETE` whose guard did not hold: a successful reply with `reason`, no `position` and no `copies_confirmed`; nothing was written |
| `copies_confirmed` | int32 | copies that confirmed |
| `served_by` | string | the node ID that ordered the write |
| `position` | string | `epoch:seq` of the applied record |
| `id` | the `_id_` value | the ID the insert used (minted or the client's) |
| `found` | bool | pop, take, get, peek, `lease_get`: whether an element, document or live lease was found |
| `elements` | array of bin | popped, taken, peeked, listed, read, claimed or leased elements |
| `keys` | array of string | `store list` and `peek` of a hash, btree or heap store, in the order of `elements`; absent for the others |
| `priorities` | array of int64 | `store list` and `peek` of a heap store only |
| `lease` | bin | the 16-byte lease ID of a claim or `lease_get` |
| `count` | int64 | `store count` |
| `more`, `cursor` | bool, bin | `store list`: another page exists, and where it resumes |
| `deduped` | bool | the answer came from the dedupe window |
| `reason` | string | with `not_applied`: `guard` |
| `guard_field` | string | with `reason`: the declared name of the first guarded field that differed |
| `document` | bin (BSON) | the scalar fields, `_id_` first: as the write left it (`return` after), as it was (`return` before), or the current document when a guard refused. Also sent with `unknown`, where the write is durable and the reply carries its `position`: the document is as certain as the position. Stores are not in it |
| `document_truncated` | bool | with `deduped`: the retry's document was over the 1,024-byte dedupe cap and is not repeated; run `get`. The first answer is never cut |
| `epoch`, `state_seq` | int64 | the node's view, so a driver can see its own is stale |

A document that is not there is `NOT_FOUND` for `peek` and `store_get`, and `found: false` for `get` and
`get_fields`; a `store_get` key that is not there, and a `lease_get` lease that is unknown, acked, released or
past its deadline, are `found: false` too, an answer and not an error (client-wire section 2). **A lost claim reply:** re-send the claim with the same request ID
(the owner answers the lease ID and no elements, `deduped`), then `lease_get` on that lease; `found: false`
means the lease ran out and the messages are back in the field, so claim again with a new request ID.

### 11.5 Errors: the payload, the detail and the new codes

The payload of an `ERROR` answer to a ring opcode is BSON `{code: int32, message: string, detail?: document}`
(client-wire section 3; the vectors encode `code` as int32). The legacy `uint8` codes `0x01` to `0x12` keep
their meaning where the ring registers the same number; a ring code above `0x12` is only ever sent in this
BSON form. **A driver acts on `code` and `detail`, never on the text** (queries Formats, "The error detail").
`detail` is one shape per code:

- `NOT_OWNER` `{owner, owner_addr, epoch, slot}` (epoch int64, slot int32 in the vector);
  `STALE_EPOCH` `{epoch, owner, owner_addr}`; `OWNER_DOWN` `{owner, missing_slots}`;
  `NO_QUORUM` `{voters, answered}`; `LEASE_LAPSED` `{node, lapsed_ms}`;
  `RF_UNSUPPORTED` `{rf, voters, data_members}` (queries Formats).
- `NOT_FOUND` carries `{expired: bool}` only on a keyed `get` of a document that exists but is past its expire time (`expired: true`); every other `NOT_FOUND` has no detail. A driver tells the two apart by `detail.expired`, never by the message, and a client wrapper such as `IsExpired` still treats both as not found.
- `PERMISSION_DENIED` carries no detail and never says whether the bucket exists: one message for a forbidden
  bucket and for an id no database has (client-wire section 3; vector `ring count: a session with no role on
  the database`).
- Every other code, `RESULT_TOO_LARGE`, `FIELD_TYPE` and `DOCUMENT_EXISTS` included, carries a message and no
  detail; a ring error with any other member is not canonical. (A `RESULT_TOO_LARGE` frame of the earlier
  engine also carries `max_result_bytes` and `retained_bytes`; a ring node does not send them.)

The ring also uses the legacy codes `NOT_FOUND` `0x01`, `PERMISSION_DENIED` `0x03`, `INVALID_ARGUMENT` `0x04`,
`UNAVAILABLE` `0x06`, `RESULT_TOO_LARGE` `0x0E` and `FIELD_TYPE` `0x10` (conventions Errors). The codes

### 11.6 Topology

`RING_TOPOLOGY` is the first call after `AUTH` for a driver that routes. A request with `epoch` 0 gets the full
reply; a non-zero `epoch` and `state_seq` that both match get `unchanged: true` and nothing more
(client-wire section 4). The full reply carries:

- `members`: `count:uvarint`, then per member `state:1 | flags:1 | idlen:uvarint | id | addrlen:uvarint |
  data_addr | clen:uvarint | client_addr`; the ranked data members, sorted by ID. State is `1` joining, `2`
  active, `3` down, `4` leaving, `5` dead (conventions section 14, as queries Formats cites it); only
  `active`, `down` and `leaving` appear. `flags` bit 0 is "the member votes"; bits 1 to 7 are reserved and a row that
  sets one is refused. `client_addr` empty means `data_addr`.
- `witnesses`: the same row layout for witnesses, which hold no documents; absent (never written with count
  0) when there are none, and **never ranked, so a driver never routes to one**.
- `voters`: int32, absent when 0; the committed voter count, which includes a voter that is on neither list
  because it is joining or dead.
- `table`: 8192 slots, each `count:uvarint` then that many rank indices (`uvarint`) into `members`, in rank
  order. A `down` member keeps its rank; the table is the full ranking, not truncated by the replication factor.
- `databases`: `[{name, id, rf}]`, listed only to a session that holds a role on the database (or on `*`).

The vectors refuse a non-canonical varint, a padded or truncated table, `unchanged` with blobs, a witness that
is also ranked and an empty `witnesses` blob (vector rows `ring topology reply refused: ...`).

### 11.7 Routing

A driver may be dumb (send keyed statements to any node, which forwards) or smart (hold the table and address
the owner); a wrong route is a redirect, never a wrong answer (queries section 4). A smart driver:

1. Sends `RING_TOPOLOGY` with `epoch` 0 after `AUTH` and keeps the answer.
2. **Routes by slot.** `placementKey = uvarint(len(database)) | database | uvarint(len(bucket)) | bucket |
   EncodeComponent(_id_)` and `slot = uint16(xxhash64(placementKey) >> 51)`: top 13 bits, 8192 slots
   (conventions section 3). No vector row pins this function (queries section 4 says the routing vectors are
   not built yet).
3. Takes `table[slot]`, truncates it to the database's `rf` from `databases`, and
   sends to the first member of that copy set whose state is not `down`. Truncating before choosing matters: the
   first non-`down` name of the untruncated ranking can be outside the copy set (queries section 4).
4. **Connects to the member's client address when its row has one, else to its data address.** The
   `owner_addr` of `NOT_OWNER` and `STALE_EPOCH` follows the same rule (client-wire section 4; vector `ring
   keyed: the slot belongs to another node`).
5. **Re-routes once.** `NOT_OWNER`: re-send the **same request ID** to the owner `detail` names, once; a
   second redirect is surfaced, never chased (queries section 4). `STALE_EPOCH`: one `RING_TOPOLOGY` refresh,
   one re-send. A connection error: one refresh; if the owner for the slot is unchanged, fail naming the node.
6. Refreshes only on these triggers: no table yet, `STALE_EPOCH`, a `NOT_OWNER` naming a node it does not know,
   a connection error. There is no poll; the request's `(epoch, state_seq)` is how the server says `unchanged`.

Re-sending the same request ID is safe. Whether a re-send is also idempotent by value depends on the
operation: queries section 4 gives the verdict per operation class, and a lost reply is never a driver guess.

### 11.8 RING_BATCH: one frame, many writes

```
+---------------+-----------+------------------------------------+
| Prologue (20) | Count (1) | Body 1 ... Body n  (n = Count)     |
+---------------+-----------+------------------------------------+
```

- The prologue is once for the frame: one routing decision, and `deadline_ms` is the **whole frame's** budget.
  `Count` is 1 to 255. Each body is byte-identical to a `RING_KEYED` body (class, 40-byte header, class
  form) and is self-delimiting, so there is no length prefix (client-wire section 7.1).
- Only the nine write classes of section 11.3; a read class is refused. A count of 0, a count past the bodies,
  a truncated body and a byte after the last body are each `INVALID_ARGUMENT`, and so is a payload that is not
  a prologue and a count: one `ERROR`, nothing done (vectors `ring batch refused: ...`).
- A 256th operation cannot be written (the count and the operation index are one byte each): a driver refuses
  it when it is queued, before sending, with `at most 255 ... Split it into batches of 255 or fewer`
  (client-wire section 7.1; vector `ring batch: 255 operations, the most a frame holds`).
- **Reply.** A `RING_REPLY` `{outcome, answers, epoch, state_seq}`. `outcome` is `ok` when every operation was
  answered with a reply and `partial` when any was answered with an error. `answers` holds exactly `Count`
  documents in request order, each `{reply: bin}` (the bytes of a lone `RING_REPLY`) or `{error: bin}` (the
  bytes of an `ERROR` payload); decode each with the decoders of sections 11.4 and 11.5 (client-wire
  section 7.2). A reply that says `ok` over an error answer is refused (vector `ring batch reply refused`).
- **Semantics** (client-wire section 7.3): no atomicity across operations; operations on the same pair apply in
  request order and others run concurrently; a refused operation does not stop the others; authorization and
  forwarding are per operation; no per-operation write concern; a batch of one answers as the lone request would.
- **Reply budget** `min(max_result_bytes, 16 MiB)`. Error answers are kept. A reply that does not fit and can be
  recomputed keeps `write_outcome`, `copies_confirmed`, `position`, `deduped`, `found`, `id`, `served_by` and the
  lease and drops `elements`, `keys` and `priorities` (a claim stays applied; read the messages with
  `lease_get`). A pop or take answer is never trimmed; one the budget has no room for is not run and is answered
  `UNAVAILABLE` (`not attempted`, `not applied`).
- **The deadline.** Operations not started when `deadline_ms` is spent are answered `UNAVAILABLE`, saying `not
  attempted`, `not applied`, and to resend the whole frame under the same request ID; they are never
  `unknown`. Which operations fall in that tail is not deterministic.
- **Retry is the whole frame, under the same request ID.** The dedupe key is `(request ID, operation index)`: a
  resent frame answers the applied operations `deduped: true` and runs the rest. A subset retry is not
  offered, because renumbered indexes would land on other operations' entries (client-wire section 7.3,
  rule 4; vector `ring batch: the deadline leaves a not-attempted tail`).

### 11.9 Vector coverage

Section 3 of this page says to ignore unknown fields and that field order does not matter. For the ring
opcodes the vectors are stricter: they refuse an unknown member, a different order and a written default
(section 11.1). Where a design document and the vectors disagree, the vectors win for bytes.

**Vector coverage.** Counted over `testdata/driver-vectors/v1.json` in this repository, rows by
`request.opcode_name`: the group named `ring` holds 202 rows, 127 exchanges and 75 refusals. Outside that
group no row sends a ring opcode.

| Request opcode | Rows | Exchanges | Refusals |
|---|---|---|---|
| `RING_KEYED` | 65 | 57 | 8 |
| `RING_ADMIN` | 53 | 37 | 16 |
| `RING_LIST` | 17 | 7 | 10 |
| `RING_GET_MANY` | 16 | 11 | 5 |
| `RING_BATCH` | 12 | 7 | 5 |
| `RING_TOPOLOGY` | 9 | 5 | 4 |
| `RING_COUNT` | 5 | 2 | 3 |

A further 22 rows of the group are refusals with no request: bytes a codec must refuse to decode, replies
included. The group also holds 3 `CLUSTER_PROBE` rows, which are node to node and not a ring opcode.

Every ring opcode has at least one row, and so does every class byte of section 11.3: the nine write
classes `0x01` to `0x09`, and the reads `0x81` to `0x84`, `0x87`, `0x88` and `0x89`, with `0x8A` (nearest)
and `0x8B` (aggregate) of `operations.md` section 4. The classes inside a `RING_BATCH` or `RING_GET_MANY`
body were not counted. No vector pins the slot function. No row sends a user command (`auth.md` section 6).
